## FINDINGS (prioritised by impact)

### 1. [CRITICAL] Predictable District / Assembly / Booth admin logins
- **Location:** `backend/services/jurisdictionService.js:89` (district = `60228001 + index`), `:117` (assembly = `60227000 + assembly no.`), `:152` / `:186` (booth = `60227680 + booth no.`). Usernames are `<assemblyname>_admin`, `<assemblyname>_b<booth>`, `ass<no>_admin`. Login check is at `:172-240`, called from `adminController.js:147`.
- **Evidence:** Code reading. This is the same code that runs live (md5 match). The repo was public until today, so the formulas should be treated as already known. DECISIONS.md (2 Oct) already lists this as OPEN.
- **Why it matters:** One guessable username plus a number gives a 7-day admin token. The token cannot be revoked: `authMiddleware.js:42-50` trusts `DYNAMIC_*` tokens completely and never checks a tokenVersion.
- **Fix:** Turn off the formula login path. Create real `Admin` records with random passwords for the people who actually use these logins; `createAdminCredential` already exists. Make `protectAdmin` reject `DYNAMIC_*` tokens. **Rotate `JWT_SECRET`** so every token already issued dies. This logs everyone out once.
- **Expected improvement:** Closes the main way in. Confidence: High.

### 2. [CRITICAL] Booth voter roll readable for any booth in the state
- **Location:** `backend/controllers/adminController.js:1654-1655`: `targetBooth = req.query.boothNo || admin.boothNo` and `targetAssembly = req.query.assemblyName || admin.assemblyName`. The admin's own area is never enforced. Route: `GET /api/admin/booth-voter-roll` (only needs `protectAdmin`).
- **Evidence:** Code reading. 100 voters per page, looping over pages and booths, gives the whole 5.68 crore roll: name, relation name, house no., age, gender, plus member mobiles where registered.
- **Why it matters:** This is a large-scale personal-data exposure under the DPDP Act 2023. Combined with #1, it needs no inside access at all.
- **Fix:** Booth admins get only their own booth. Assembly admins get only booths in their assembly. District admins get only assemblies in their district. Return 403 otherwise. Same pattern as the volunteer-export fix from earlier today.
- Confidence: High.

### 3. [CRITICAL] Area filter can be replaced in list and export URLs
- **Location:** `adminController.js:695-697` (applications list), `:1220-1222` (CSV export), `:1321-1323` (Excel export). `appScopeFilter.district = <query value>` **overwrites** the admin's own district, assembly or booth.
- **Evidence:** Code reading. A Booth admin sending `?district=X&assemblyName=Y&boothNo=Z` gets that booth's members. A District admin can loop over all 38 districts. Exports include name, EPIC and mobile.
- **Fix:** AND the requested filters with the admin's own scope, so they can narrow it but never widen it. Same approach as `exportVolunteerRequestsExcel` (`:2280-2286`).
- Confidence: High.

### 4. [HIGH] Leaked secrets
- **SMS key:** an old 2Factor API key was hard-coded in `smsService.js`. It has since been removed from the code but is **still in git history**, and the repo was public until today. → Rotate it in the 2Factor dashboard unless it has already been rotated.
- **JWT example:** `PRODUCTION_READINESS_AUDIT.md:209` contains a concrete 64-hex `JWT_SECRET`. If the live `.env` was copied from that file, admin tokens can be forged. → Check that the live value is different (I did not read `.env`). Rotating it as part of fix #1 settles this either way.
- Confidence: High that both are exposed. Unknown whether they are still in use.

### 5. [HIGH] Voter-lookup endpoints leak more than needed
- **Location:** `POST /api/validate-epic` (`userChatController.js:217-228`) returns name, father/husband name, age, gender, booth (part) no. and serial no. for **any** EPIC, without login. `POST /api/voter/search-epic` (`voterController.js:27-31`) says "already registered under mobile ending in …1234".
- **Limits:** 10 per 10 min per worker, so about 40 per IP per 10 min. Logs show 1,502 successful lookups in 14 days, which looks like normal use.
- **Fix:** Return only what the confirm screen needs, and mask the rest (for example, first name plus district/assembly). Drop the mobile-ending hint. Move rate-limit counters to a shared store (see #8).
- Confidence: High.

### 6. [HIGH — speed] Members download far more than they need
- **Scheme images:** 32 PNGs totalling **15.0 MB** (average 481 KB, largest 1,026 KB), served from `/uploads/schemes/`. They are used as CSS backgrounds (`ChatbotPage.jsx:1919-2064`), so the browser cannot lazy-load them.
- **JavaScript:** one bundle, `index-BAFHGJWK-v2.js`, is 2.23 MB raw and **622 KB over the wire** (gzip). About 347 KB of that is admin-only, including exceljs. This is already noted as "batch 2" in DECISIONS.md.
- **Fix:** Convert images to WebP at the size actually displayed (target 40–60 KB each, so ~1.5 MB total instead of 15 MB) and render them as `<img loading="lazy">`. Split the admin portal into its own chunk with `React.lazy`.
- **Expected improvement:** About 90% less image data and about 55% less JS for members on mobile data. Confidence: High.

### 7. [MEDIUM] Registration trusts what the browser sends
- **Location:** `userChatController.js:297-376` (`register-schemes`) and `boothPresidentController.js:272-331` (`volunteer-register`). EPIC, name, district, assembly and booth come straight from the request body. Nothing re-checks them against the voter DB on the server.
- **Why it matters:** Anyone with a working phone number can register under someone else's EPIC, or claim any district or booth. That inflates numbers and pollutes area dashboards.
- **Fix:** If an EPIC is given, look it up on the server and use the voter-DB values. If not, keep the `PND-` path but validate district/assembly against `getAssemblyMetadata()`.

### 8. [MEDIUM] Rate limits are 4× weaker than they look
- **Location:** `server.js:98-148`. `express-rate-limit` with its default in-memory store keeps a separate count in each PM2 worker.
- **Real limits:** OTP 24 per 10 min per IP, admin login 60 per 15 min, EPIC lookup 40 per 10 min.
- **Fix:** Use a shared store. Mongo is already there: `rate-limit-mongo`, or a small custom store with a TTL collection.

### 9. [MEDIUM] Browser-side token safety
- **CSP:** the live CSP on the site is `default-src 'self' https: data: 'unsafe-inline'`. That allows inline scripts and any HTTPS host.
- **Tokens:** user (7-day) and admin (7-day) tokens live in `localStorage` (`AuthContext.jsx`, `ChatbotPage.jsx:194`).
- **Rich-text renderer:** `formatRichText` (`ChatbotPage.jsx:230-250`) inserts URLs into `href` **before** escaping them. Today only the user's own text reaches it, so the risk is low, but it is a trap for future changes.
- **Fix:** Tighten the CSP (`script-src 'self'` plus the Sentry host) and escape URLs.

### 10. [MEDIUM] Unescaped regex in volunteer search
- **Location:** `boothPresidentController.js:177` (`assemblyName`) and `:185` (`search`). Both go into `new RegExp(...)` raw. Admin-only, but one crafted string can stall a worker.
- **Fix:** Use the existing `escapeRegex`.

### 11. [MEDIUM] WhatsApp endpoints
- **Webhook:** `whatsappWebhook.js:40` only checks the signature *if* `META_APP_SECRET` is set. → Confirm it is set on the server. Better, refuse unsigned posts.
- **Flow endpoint** (`whatsappFlow.js`, disabled at `:199`):
  - It takes the member's phone from `flow_token` (`reg_<phone>` / `svc_<phone>`).
  - It accepts **plain unencrypted JSON** if `FLOW_PRIVATE_KEY` is missing (`:28`).
  - It does not verify Meta's signature.
  - → Fix all three **before** re-enabling (TASK-22). Otherwise anyone could read or register any phone number's profile.

### 12. [MEDIUM — scale] Will slow down as data grows
- **Exports in memory:** Excel/CSV and `isExport` mode load every row at once (`adminController.js:686`, limit 500,000; `:1460`). Today that is ~500 applications, so it's fine. At lakhs of rows it would run a worker out of memory.
- **Regex filters skip indexes:** area filters use `/^X$/i`, which MongoDB can't serve efficiently from an index. → Store a normalised uppercase district/assembly and filter by equality.
- **Coverage scan:** Assembly/Booth coverage (`getCoverage`, `:1932`) runs `$group` over a whole voter collection (~2.5 lakh docs) every 2 min per scope. That is the same pattern fixed for the dashboard today. → Reuse `loadAssemblyBoothCounts`.

### 13. [MEDIUM] Misleading audit document
- `PRODUCTION_READINESS_AUDIT.md` claims "hardcoded passcode formulas permanently removed", "credentials in MongoDB with bcrypt" and "unique indexes added". None of these is true in the current code. It also contains the example secrets mentioned in #4.
- **Fix:** Mark it superseded, or delete it, so nobody relies on it.

### LOW
- **14. Duplicate applications:** prevention is check-then-insert with no unique index on `{userId, schemeId}`. A double-tap can create two applications (`SchemeApplication.js:96` is not unique).
- **15. OTP session reuse:** a verified OTP session stays valid for up to ~15 min and is not consumed after registration. The JWT path in `register-schemes` and `volunteer-register` ignores `tokenVersion`, so a token that was logged out still works there.
- **16. Weak OTP randomness:** OTP is generated with `Math.random()` (`userChatController.js:26`). → Use `crypto.randomInt`.
- **17. Statewide count leak:** the "Incomplete registrations" count on the dashboard is statewide for every role (`adminController.js:267`).
- **18. Empty-scope admins:** an admin created as `DISTRICT_ADMIN` without a district sees the whole state (`getAdminScopeQuery` returns `{}`). `createAdminCredential` doesn't validate this.
- **19. Mobile numbers in logs:** full mobile numbers are written to the PM2 out log (`userChatController.js:345`).
- **20. Housekeeping:**
  - nginx `/health`, `/admin/api` and `/upload` are leftover routes (`/health` returns 404).
  - `frontend/dist.tar.gz` is tracked in git.
  - Untracked junk sits in the repo root.
  - `backend/controllers/referralController.js` has an **uncommitted local change**.
  - ufw is inactive. The DO cloud firewall covers this, but next-server is bound to `0.0.0.0:3001`.
- **21. SVG uploads:** scheme image upload accepts SVG (`localSchemeImageService.js:15`). Super Admin only, but SVGs served from the same origin can carry script.
